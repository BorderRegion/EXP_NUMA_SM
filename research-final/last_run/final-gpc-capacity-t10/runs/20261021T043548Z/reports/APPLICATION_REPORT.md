# 实际GQA容量分工结果

**四锚、append+attention scope、六动作、两独立确认进程，共48主标签均完成；没有超过原N19。** 没有按收益跳过负例。受限分支不作精细显著性结论。

保持原16B搬运、QK、softmax、W、worker身份、page序列、partial地址和merge顺序。唯一任务坐标改变为`task=task_begin+blockIdx.x`，GPU每launch只接收begin/count标量。五组范围覆盖每个完整worker一次；无新逐任务LUT、调度kernel、SMID派工、CPU中途等待或transpose。正式DIRECT SASS含128-bit load，无SMID/clock读取和local spill；诊断兄弟版本单列。

一次Graph包含五个producer+原merge；CUPTI四次CAP调用看到20个producer和4个merge，最大5个计算kernel重叠。Graph一次提交不等于一个kernel。全56SM的E56_DIRECT保留相同range visitor；N19保留SHORT最后到达融合、LONG/GQA8的BLIND以及RAGGED DIRECT。

两独立开发过程提供五组孤立和SM_PROP并发容量，共48容量phase；正式CAP采用一次并发proxy work/自身event span修正的等权几何均值。未迭代、未用确认数据调权。WRONG固定左轮转五个权重。开发冻结BEST_SIMPLE四锚都是N19。有限分支只拟合append scope，其他scope及8个新形状均NA。

## 正确性、工程问题与成本

本轮CPU审计逐项核对768份有效数值记录，其中496份DIRECT参照检查；有参照哈希的正式/开发记录逐字节hash一致。独立资格覆盖四锚两scope，trace每逻辑页访问恰一次和GPC成员匹配；append只改目标末位置，非目标KV保持。有限memcheck/synccheck均0 errors，不等于任意并发/COW安全证明。

两个开发失败均保留：捕获内诊断事件未物化导致elapsed读取失败，修复为EXTERNAL timing events（只在诊断图）；随后DEV与kernel mode字段重名导致元数据异常，修复为嵌套字段。完整块在冻结前重跑，已保存的不完整容量数据单列，未用于选择。旧sanitizer启动缺注入库，改用本机既有完整12.8.93工具，不安装任何依赖。

OPPORTUNITY_BUDGET先于CAP权重冻结和实际确认；通用range适配代码此前已编译，因此不是“在编写任何适配代码之前”的预算。初始化资源/Graph成本在PLANS记录，历史推荐API初始化见FAST_GQA。未观察到对N19的正稳态节省，H=1/100/1000都不能据此得到有限回本点。代数账单与校准成本另见COST_ACCOUNTING.json，不把Graph构建费当完整生产初始化。

本实验suite预建五组资源以做同夹具比较，N19正式样本也处于该夹具；它不是原生旁路初始化成本的证明。实际推荐LocalityPlan原接口未改、不会创建Green组；预定24个GEMM旁路条件在受限分支未执行。

64步跨页长度增长、8个新形状、早晚3+3、60分钟长程、恢复状态三块敏感性均未运行，逐项NA。有限append是变化的新KV写入当前末token位置，不冒充真实长度增长、真实模型或tokens/s。
