# 工作负载、数据隔离与正确性要求

## 1. W1：本地现成的 CUDA 3DGS

**来源与版本**：使用现成的 Graphdeco（headless 版本）或可编译的兼容版本。锁定 commit 与依赖版本。

**场景划分**：
- Train 与 Bonsai：开发与主测试场景。
- Truck：只作为最终留出（held-out）场景，不参与任何调参。
- 每个场景预先按相机 ID 划分为 2 条开发轨迹、2 条测试轨迹。各轨迹互不重叠。
- 曾经被看过、用过的相机 ID 不能称为“完全未见过”。如有这种情况，必须如实披露。

**输入统一**：
- 所有平台尽量使用相同的模型、相机和配置（记录 hash）。
- 第一轮的共同分辨率为 720p。
- 显存和时长允许时，两张卡再加做 1080p。
- **不能**出现“5070 Ti 只报 1080p、T10 只报 720p，却仍称为同输入比较”的情况。

**允许改动的范围**：
- 只改变**完整 tile 的执行安排**。
- 保持不变的内容：preprocess、binning、sort，原始 Gaussian ID，tie 的顺序，alpha 累积，early termination，精度，SH 配置，深度规则。
- helper 与 evaluator 只做“逻辑 tile 索引的替换”，并保存代码 diff。

**任务列表的生成**：
- 每帧的 ranges 与 point_list 仍然按真实相机生成。
- SCENE_PLAN 不能先从测试帧读回任务列表，再无偿地选择任务分组。
- 离线记录的快照只归类为 `MECHANISM_SNAPSHOT`，不能外推为动态结果。

## 2. W2：独立的本地稀疏行任务（有资源时进行）

**输入要求**：
- 使用本地已有的 CSR 或稀疏 gather 程序。
- 至少两个有来源、且没有为本方法专门挑选过的矩阵输入。

**计算规则**：
- 每一行完整计算。行内顺序不变。跨行的任务相互独立。
- 方法只改变“行的分配”。**不能**把 W1 的同一个 evaluator 改个名字，当作第二个程序。

**原生参考**：需要强的原生参考，包括：
- 同一个原生的 row kernel。
- 本地可用的 cuSPARSE，或其他现成的优化实现。

如果 cuSPARSE 的算术顺序不同，应在预先登记的数学参考与有限误差合同下，单独比较生产时间。
主比较 M/B（同 body）仍然要求逐位（bitwise）一致。**不能因为与外部库比较而放宽这一要求。**

**没有既有 W2 或真实矩阵时**：
- 可以生成具有固定分布的整数 CSR，用于机制对照。这种输入必须标记为 `SYNTHETIC`，**不算作独立的真实工作负载**。
- 不下载数据，也不花一周时间重写通用的稀疏库。
- CPU 模型允许 uint32 的模 2^32 精确结果。

## 3. cluster 真实内核的补充（不是新建第三个系统）

**RTX 5070 Ti**：
- 如果本机已经有**原本就使用 cluster 或 DSM** 的成熟库内核（例如已经能运行的本地库示例），优先用它来填 E2 中 cluster 机制的位置。
- 最多替换一个人工的资源核。仍然在 E2 cluster 机制的 96 sessions 上限之内。
- 保存它的默认最佳配置，以及调优后的非 cluster 基线和不同 cluster 尺寸的基线。
- **不能**刻意选择慢的 cluster 设置来制造空间。

**T10**：
- 只运行本地支持的、功能等价的普通版本，用于本机比较。
- 不能把两者的机器码或性能直接当作裁剪的因果证据。
- 没有现成的库时，保留人工 DSM 机制，并明确写出“实际 cluster 应用证据缺口”。**不能从零移植新库。**

## 4. 共置（E5，最多三对）

**选择任务对**：
- 优先选择确实需要同时完成的两路视图，或两个独立的稀疏任务。
- **不能**把单帧人为拆成两个应用。
- 要明确标注：“同一程序的双视图”与“独立程序的并发”是两种不同的情况。

**基线**：串行 Native、普通多 stream 并发、按 SM 数量的 Green 分区、单速率、候选方法。
从中冻结四种最强或必需的对照。所有方法都必须完成同样的两项工作。

**记录的指标**：
- 双方各自的完成时间与总 makespan。
- 相对独立执行的 slowdown。
- 总吞吐。
- 吞吐收益不能写成单帧延迟的降低。

**禁止新增**：持久服务、网络 benchmark、LLM 推理系统、SLO 控制器。

## 5. 正确性要求：够用即可，不做无尽的调试工程

**每种新 kernel 或执行器的首次资格测试**：
- CPU 上恰好一次小规模域的完整枚举，加上一个小的 GPU 任务。
- 若平台支持，做一次有界的 memcheck 与 synccheck。
- 已经验证过的模块，不在每次 run 中重复运行 sanitizer。

**整数微核**：CUDA 结果必须与完整的 CPU 模型一致。**不能只检查 checksum 而忽略真实的读取是否发生。**
对流式任务，要让每个 CTA 写出真实结果，并检查编译后的 load 指令没有被优化掉。

**W1 的资格测试**：
- 每个策略使用 16 个预先固定的帧，检查完整的 color、final_T、n_contrib。
- 这 16 帧要覆盖：空 tile、重 tile、321×181 的边界视口，以及正式分辨率。
- Native 自身重复三次，结果必须一致。
- 同 body 的候选方法，要求与 Native 逐位一致。

**W2 的资格测试**：同 body 的候选方法，按原始行顺序，要求逐位一致。外部库使用事先固定的参考合同。精度与输入全部记录。

**资格测试的范围**：必须覆盖正式路径、执行顺序、长度与 reset。至少完整跑一次 512 帧的流水线。
计时模式与资格模式，只允许在“额外的读回或诊断”上有区别。**不能悄悄改变 warmup、slot 或同步方式。**

**正式运行**：
- 每个 session 结束时，对最终的完整输出做比较。
- 预先确定的前、中、末三帧要保存下来。
- 每帧记录轻量的 digest 作为 screen 判据。它不替代完整的资格测试。
- 日志和读回不计入计时，但要披露其共同成本，以及可能的缓存扰动。
- E5 最多用 12 个 sessions，专门比较“关闭逐帧 digest”的敏感性。

**失败处理**：
- 默认隔离失败的变体或条件，记录第一个差异点以及完整产物。
- 基于一个具体错误做一次修复后，重新资格测试。原来的失败记录不能删除。
- 不能因为很小的差异就自动加一个 epsilon 放行。也不能无限期地展开浮点精度调查。
- 如果 Native 自身无法重复、越界，或设备丢失，停止受影响的 GPU 分支。CPU 整理工作继续进行。

## 6. 正常 kernel 的时长

- 探针的目标时长 < 2 ms。不用 sleep 或 spin 来延长驻留时间。
- 先小后大。若某次运行超过预先登记的 20 ms 上限，就减小机械规模，并记录下来。
- 应用的规模以健康的原生基线为准向上放大。
- 长时间的执行，是许多有界的 launch，而不是一个常驻 kernel 连续运行半小时。
