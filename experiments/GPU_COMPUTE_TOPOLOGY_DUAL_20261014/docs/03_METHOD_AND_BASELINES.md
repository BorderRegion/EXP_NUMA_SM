# 唯一的方法：类型化有效容量的初始化静态计划

## 1. 方法合同与数据形式

**目标**：在给定的实际资源集合 g 上，按照校准得到的各类工作的有效服务能力，分配**完整的逻辑任务**。
不猜测未来的缓存命中，也不在每一帧读回任务元数据。

**输入**：
- 真实可控的组（见 `docs/02`）及每组的 SM 与 cluster 资格。
- 在有代表性的并发下测得的有限服务曲线。
- 开发输入上的任务类别与工作量估计。
- 当前分配的 generation 编号。
- 合法的任务空间。

**输出**：只读的 task→group/worker 表，或压缩后的 offset/stride 规则。正常 launch 只读取表或常量，然后执行。
本轮的主方法**不包括**全局任务领取队列，也**不包括**每帧 CPU 规划器。

**适用范围必须标注**，三种之一：
- `DEVICE_PLAN`：固定的 kernel 与规模类别、资源布局。
- `SCENE_PLAN`：使用校准相机得出的静态 tile 权重与类别。不保证对所有相机都最优。
- `SNAPSHOT_PLAN`：已知当前快照真实列表的静态分配，只用于估计机会上限。它**不能**当作动态帧的部署结果。

## 2. 简单、可执行的计划算法

1. **工作类别**：最多 3 类。例如低、高算术强度，或不同的资源状态。真实渲染的分类，由开发数据上的固定规则形成。测试集上不允许用当前耗时反推分类。
2. **时间预测**：`p[t,g] = work[t] / rate[g, c(t)]`。服务曲线可以分为最多两档并发负载。速率同时有隔离和并发两种标定；主候选使用预先登记的那一档并发。
3. **初始化贪心**：
   - 按任务在各组之间的预测差距（spread）与权重，从大到小排序。
   - 把每个任务放进能使全局预计最大完成时间最小的合法组。
   - 若出现并列，按预先固定的 group ID 决定。
   - 最多做一次边界局部交换扫描，不做无限制的调参。
   - 只有已知的资源限制和 cluster 资格会影响哪些组合法。
   - 若没有可靠的任务类别，就退化为单速率。此时必须报告：本方法在实际上是否等价于基线。
4. **参考实现**：`tools/reference.py` 给出小规模的 CPU 参考。它是标准的 minimax 启发式，**不自动等于论文创新**。
5. **大场景的粒度控制**：不能做 O(tasks²) 的分配。按固定的空间 macrotile 压缩分配粒度，规划单元最多 4096 个。每个 macro 内部保持原始的逻辑顺序。粒度可选 1、4、16 个 tile，最多校准 3 档。

**计划的生命周期**：
- 对每个新的 scene 或新的分配，在初始化时构建一次固定计划。正常的相机移动不重新构建。
- 画面宽高改变，或容量增长时，可以重新构建计划。这项成本计入生命周期，不能藏在 warmup 中。

## 3. 实际执行器

**首选 Green 独立流**：每组内有多个 CTA，按初始化任务表或 stride 处理自己负责的完整 tile 或 CSR 行。
- 每个 CTA 循环中，每个 tile 开始前重置 private 与 shared 状态。
- 所有线程以一致的 CTA 控制路径参加 barrier。
- 最后要有明确的 barrier，避免跨任务的覆盖。
- **不使用旧设计中的 atomic claim 来动态领取任务。**

**每组的 grid 大小**：在该 kernel 实际 occupancy 的 1× 与 2× 两档之间选择。不强制一个 block 对应一个 SM。
必须保证：每个任务且仅执行一次。空闲 SM 或尾部组不能丢弃任务。

**没有 Green 时的替代方案**：在标准的 cooperative launch 中，执行一次 roster 收集和合法的 `grid.sync`。归属在静态阶段确定，处理有限的任务。这只有一个替代实现。
如果某个组缺失，按确定的规则把其任务重新分给在场的 worker。不忙等，也不再次 launch 去重新扫描漏掉的任务。
额外的 roster 与 barrier 属于运行时成本，**不能称为零成本**。

**普通 grid 的特殊情况**：`tileTable[blockIdx]` 只改变执行顺序，**不改变物理放置**。记录为 `ORDER_ONLY`。它的结果不能用来支持任何拓扑结论。

## 4. 静态表与编译期常量

1. **先实现表（table）版本。** 普通的 SER、FP 与 tile 算法都不改动。
2. **常量版本**：只把同一张表中、能表达为小 offset 或 stride 的部分特化为编译期常量。最多 4 个实例。
   - 不展开所有帧的输入。
   - 不把设备绝对指针编码进去。
   - 比较的是**同一份计划**下的 table 与 constant，而不是两种不同的分配。
   - 常量版本未通过资格测试，可以单独排除，表版本的实验继续进行。**不能因为一个常量版本失败就暂停整个项目。**
3. **零在线规划的验收条件**：`planner_calls = 0`、`schedule_D2H = 0`、`schedule_H2D = 0`、`steady_recompile = 0`。
   - `extra_launch`、表读取（`table_reads`）、地址运算和控制设置可以非零，且要计入耗时。

## 5. 正式的八个策略

| 代码 | 含义 |
|---|---|
| **N** | 优化过的原生执行，不修改调度结构。**必需参考。** |
| **I** | 同一执行器，拓扑盲。按实际 SM 数量分配大小相同的逻辑任务。 |
| **S** | 同一执行器，固定的空间顺序（Morton 或 tile 顺序）加 SM 比例。用于检查纯粹的局部性效应。 |
| **L** | 使用相同的开发任务权重，但把每个 SM 视为相同的单位服务能力（按 SM 数量）。 |
| **R** | 使用相同校准日志，每组**单一速率**的加权分配。**必需的强简单基线。** |
| **T** | 按 SM、GPC 或 cluster 合格数量的简单拓扑启发式。只有真实证据支持时才运行，否则记为 NA。 |
| **M** | 本方法：类型化、并发校准的静态 minimax 候选。**全部实验中只有一个。** |
| **P** | M 的预先固定置换版本：对容量与类别表做置换，再用同一算法分配。资源份额与任务集合保持不变，并输出任务权重的分布。 |

关于 **P** 的额外规定：如果各组的份额不同，**不能**简单地整体交换任务列表，否则会造成额外的不均衡。
应在相同类别或工作桶内置换，并记录差异。这不能被说成完全隔离的拓扑干预。

**其他规定**：
- **N 和 R 是必需的主参考。** 若 M 与 R 完全相同，报告 `plan-overlap=100%`，并且不宣称新方法。
- **T 因物理图不足而不可用时**，保留缺格（NA），**不能**用重复的策略来顶替。
- 最多八个策略设置或有限的超参数校准。所有有参数的基线使用同样多的调参机会。
- 本地如有成熟的生产后端，补充生产参考 `Bext`。“同代码 layout 的因果效应”和“最佳生产吞吐”是两个不同的问题，要分开回答。
- 如果生产后端的语义不同，只做描述，不把质量较低的结果拿来比较。

## 6. 需要的机制证据

- 布局、组能力、计划与实际执行之间的对应表。
- 每组实际的任务数、权重与完成区间。
- 在独立数据块上，单速率或类型化预测的误差。
- 隔离标定、并发标定与最终选择之间的区别。

如果收益来自 remapping 或多 context，**不能归因于芯片裁剪**，除非对照已经排除了普通分组、局部性和负载变化的影响。
更高层的论文可以定位为“容量感知”的方法。裁剪只是动机，不必写进标题。

## 7. 为什么不直接选“性能最好的组”

每个方案必须保持**相同的总资源**。如果一个任务获得了更好的位置或更多 SM，其他任务也要执行，并且计入 makespan 或各自的 SLO。
没有公平的余数或共置工作，就不能声称整卡吞吐增益。

**条件式分支**：如果 cluster 只在部分 SM 上可用，其余 SM 可以执行普通 CTA 的互补调度。这只在**已有应用任务本身需要 cluster** 时才进入。最多一个混合 launch。不能为 renderer 添加 cluster。
原生的最优非 cluster 方案必须保留，作为对照。
