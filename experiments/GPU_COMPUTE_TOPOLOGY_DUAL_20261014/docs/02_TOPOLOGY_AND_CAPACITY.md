# 拓扑、cluster 资格与有效容量：必须真正测量的内容

## A. 三层数据

本包把数据分成三层，不再用一张热图代表全部结论。

1. `SKU_FACT` / `DEVICE_QUERY`：产品总量，以及实卡实际查询到的能力。
2. `SAME_GPC_EDGE` / `CONTROLLED_GROUP`：cluster 共现证明“同一 GPC”；Green 实际包含的 SM 定义“可控组”。两者不是同一个概念。
3. `EFFECTIVE_CAPACITY(g, kernel, config, concurrency)`：某个具体执行集合 g，在某种并发条件下处理某类工作时，实际的服务能力。

存活的 SM 不会因为“来自裁剪过的卡”就天然变慢。计算上的不对称通常体现在：组内 SM 数量、cluster 可用性、片上共享资源，或分区组合方式上。而不是每个保留下来的 SM 都残缺。

## B. RTX 5070 Ti 的 cluster 部分拓扑

只在实际支持时运行。先 query `clusterLaunch`、kernel 的最大 cluster 大小和 active-cluster 容量。
“支持的上限”和“哪些 SM 能被某种 cluster 使用”是两件事，要分开记录。

- cluster 尺寸候选：1、2、3、4、6、8。其中实际合法的最多 6 种。
- block 形状：128 或 256 线程。工作量有限。每个新进程运行 3 次；每个尺寸、形状最多 12 个 launch。
- 每个 CTA 写入：`launch_id`、cluster 逻辑编号、cluster 内 rank、SM 起止编号、任务结果。
- 32 和 64 只是诊断输出的规模，不假定它们会被物理分发到特定位置。

同一个 cluster 内观察到的不同 SM，可以合并为一个同 GPC 的组件。**不能把不同 launch 的 `cluster_id` 直接当作同一个物理组。**
如果反复合并后仍有多个子组件，就保留为 `partial`。

没有出现过的 SM **不是**“不支持 cluster”的直接证据。结合普通覆盖、尺寸扫描、occupancy 与多轮记录，只能说“在此配方下未观测到”。

附带的 starter 不是完整的拓扑算法。必须如实记录每次支持或失败的返回码。**不能为了让表格填满而使用不支持的尺寸。**
不要假定每个 cluster 的 block 落在不同的 SM 上；复核推导前先去重。

## C. T10 与无法完整恢复 GPC 图的情况

T10 默认没有硬件 cluster。普通 grid 记录的 SM 顺序不提供 GPC 映射，**不能用 `SM_ID // N` 之类的公式补全图**。

如果本机的公共 Green 可用，就测量它实际的 SM 集合和类型化的服务能力。
最多做一次有界的 L2 竞争指纹诊断，用来提出经验类别。但只有存在合法的可控集合时才执行。
缓存容量、频率和竞争都会影响结果，**不能自动成为物理 GPC 标签。**

未形成完整 GPC 图，不阻塞服务能力建模和真实的同机 A/B 对比。如果论文只有经验性的容量映射，要明确写出其归因边界。

## D. 公开的分区选择（不是任意 SM 绑核）

只使用本地 header 或 API 实际提供的接口。版本缺失某个参数时，不猜参数。最多 4 种 layout：

- **G0**：单组，包含全部可用 SM。用于控制同机制的开销。
- **G1**：两组，各接近一半，外加任意余数组。
- **G2**：两组，约 1/3 与 2/3，按实际粒度对齐，并保留所有余数。
- **G3**：本机明确支持的另一种组内 co-scheduling 或 grouping 模式。不存在则记为 NA。

资源份额必须来自 query 结果，不得硬编码（例如不能写死 5070 Ti = 32/32/6，或 T10 = 某个数字）。
组数上限为 2–4。剩余的 SM 也要执行有意义的工作，**不能悄悄丢掉它们，却仍称为满卡。**

每个 layout 记录：实际 SM 集合、重复或交叠的 SM、`observed_count`、`requested_count`、event 与 context 的所有权。
相同的 SM 配额、不同的物理位置，只比较真实能够获得的组合。如果 API 无法提供，标记为 `PARTITION_CHOICE_LIMITED`。

分区之间**不做 spin 等待**。先在主 context 中同步完成初始化，然后提交全部独立的 consumer，最后统一 join。
事件计时在各自的 context 内进行。跨 context 只用 CPU 的 ready 时间范围，或工具支持的统一时间线。

全卡的最优原生 grid 可能优于任何显式分区，这个结果必须接受。

## E. 四种有输出的微核家族

- **K0 `UINT_COMPUTE`**：独立的 u32 递推，多条链的 ILP，输入已初始化。使用精确的 CPU 模型。禁止没有结果的空循环或用 sleep 占用时间。
- **K1 `RESOURCE_SENSITIVE`**：真正有用的共享 tile、reduction 或寄存器状态，共三种真实形状。不能只为了强制“一个 SM 一个 block”而塞入大量用不到的 shared memory。
- **K2 `CACHE_REUSE`**：完整声明的数据被多次使用。工作集按实卡的 L1/L2 大小选择，并记录实际访问的集合。普通加载或 `.cg` 只是一种缓存配方，不保证硬件的服务层级。
- **K3 `STREAMING`**：数据完全分离，访问连续且量足够。记录实际的唯一字节数。吞吐量不等于裸延迟。

每个家族最多 3 种规模：small、nominal、large。规模按资源和运行时长选择，**不按哪个更快来选**。
跨卡时，既报告相同绝对输入的公共集，也可以附加按本卡 L2 或 SM 数缩放的机制集。两者不合并统计。

“同组独立运行”与“所有组同时运行”两种测量，任务集必须完全相同。
隔离标定会高估并发能力。因此候选方法必须在少数预先登记的并发点上校准，并独立验证。

## F. cluster 碎片化机制（5070 Ti 的扩展，不强加给应用）

对于 k=1、2、4、8 中被支持的项，测试两种 kernel：一个普通的计算 kernel，以及一个真正使用 DSM（分布式共享内存）或 cluster 同步的局部共享 kernel。
每个 kernel 自己的资源、occupancy 和 query 支持情况，是判断依据。逐行保存 SM 覆盖与未覆盖的记录。性能测试在去掉诊断输出的版本中进行。

公式 `sum(floor(S_g/k)*k)` **只能**在“每个 block 恰好占一个 SM”的理想假设下用于说明。它不能替代真实容量。真实的 CTA/SM 驻留、cluster 映射和资源上限都必须测量。

算例、软件限额和人为禁用 SM 只是模拟，**不能冒充物理 floorsweeping。**
原生 3DGS 没有 DSM 需求时，不得给 Native 硬加 cluster，再通过取消它来制造优化。

## G. 正式的因果对照

主对照在同一台机器上进行，使用相同的逻辑工作与相同的内存内容，包括：
- Native（原生执行）
- 同资源、同 kernel 的盲映射
- 按 SM 计数的映射
- 按独立（isolated）速度的映射
- 按并发类型化速度的映射
- 预先固定的同配额置换

类别之间的容量差异，用 held-out 的 launch 或进程做确认。**不能在同一张训练热图上挑出快的组，再用相同样本报告收益。**
群组容量要记录 tasks/ms 与并发批次的完成时间。**不能用不同 SM 上的 clock 值相减。**
诊断记录可以用于判断设备位置是否合格，但不能证明每个正式任务都已记录了位置。

## H. 开销不能用无关的 kernel 相减得到

以下三者来自不同的工作，**不能**互相相减，来做“预测收益减去微核开销”：
- 某个工作的标定速度
- 简单 gather 的 Green 开销
- renderer 的 frame time

只有同一输入下的 Native、I、R、M 对照，才能用于分解实际成本。

任何吞吐差异，都要先区分：kernel 执行、host 提交或初始化、资源比例、L2 与显存竞争。
没有 counter 数据时，不能把某个具体的硬件机制写成已经证实。
