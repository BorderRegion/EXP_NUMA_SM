# Codex 主任务书：裁剪 GPU 的有效容量与低在线成本调度

## 0. 本轮授权、目标与不扩张项

- 用户分别在两台本机运行 Codex：**Tesla T10 16GB** 与 **RTX 5070 Ti**。目标是发表一篇 GPU infrastructure 论文。
- 主线：在资源分区或执行约束下，利用实测的计算拓扑和与工作类型相关的有效容量，在初始化阶段形成执行计划；稳态时直接执行该计划。
- 连续完成 E0–E6（见第 4 节）。普通的构建、路径、记录问题，以及有证据支持的小型同步修复，由 Codex 自行处理。每个阶段结束写一份简短的自动摘要即可。**不要**在 smoke 测试、第一张热图或第一份 CSV 出来后请示。
- 本轮的终点是一份可用于研究决策的完整报告，而不是不断增加验收工程。
- **不恢复**旧 V3、SER compiler、证据检查器、每帧 CPU bundle planner。
- RTX 5080 的旧结果只读。它不能作为两张新卡的配对基线，也不要重跑旧实验。
- 没有用户另行授权时，**不得**：购买新设备、租用新实例、升级驱动或系统、下载依赖、使用 SSH 或代理。
- 平台实际占用的费用，按账单或单价记录。单价未知时填 `null`。**不能**因为“没有新增采购”就把实际成本记为零。
- 本轮最多一个新候选方法，以及一个公共 Green 后端。若没有 Green，可以允许一个小型、有界的 cooperative 静态分配后端作为替代。两者不得并行扩展成通用运行时。
- cluster 只有在硬件能力支持时，才作为独立的约束或机制使用。它不是必须强加给 renderer 的工作。

## 1. 研究问题

- **H1**：裁剪或分区使“SM 数量”不足以预测某类 kernel 的有效容量。现有原生调度是否已经吸收了这种不均衡，必须实际测量。
- **H2**：在相同的 SM 配额、相同的逻辑任务、但合法的物理资源组合不同的情况下，这种差异依然存在。它不能只来自频率、带宽或工作负载的差别。
- **H3**：在初始化阶段使用**类型化的有效容量**，可以生成静态任务映射。在有代表性的并发条件和完整输入下，它应当优于按 SM 数量分配和单速率的简单分配。
- **H4**：该方法至少能改善一个真实程序的完整成本，或给出明确的吞吐与延迟权衡。普通的原生执行不能被隐藏。
- **H5**：T10 与 RTX 5070 Ti 的支持范围可以解释。缺少 cluster 属于特性缺失，而不是算法失败。跨卡的总耗时不是 floorsweeping 的因果效应。

工作标题暂定为 `Effective-Capacity Static Scheduling`。只有物理证据充分时，才使用 floorsweeping-aware 一词。若只测得了可控分区之间的差异，则称为 capacity-aware 或 partition-aware。**不默认使用 NUMA 一词。**

## 2. 必须完成的核心工作与优先级

**P0（核心，必须完成）**：
- 两个平台的原生 CUDA 资格测试与真实工作负载。
- 实际的资源组，以及覆盖情况。
- 四类 kernel 的吞吐与并发曲线。
- 同一机制下的分配 A/B 对照。
- 完整的初始化成本与稳态时间。

**P1（重点，有余力应完成）**：
- RTX 5070 Ti 上 cluster 的共现与资格测试。
- 原生与 Green 配额的效果。
- 单一候选方法的实际部署。
- 真实的 tile 渲染，以及第二个独立程序或算子。
- 若存在独立增量，再做留出测试与生命周期测试。

**P2（可以缺项）**：
- 精确的 SM→GPC 图。
- 原生微架构 counters。
- 物理内存域。
- 额外的外部后端。
- P2 不完整时，**不能**反复阻塞 P0。

实现的优先顺序：可运行的 runner 与基线 > 有实际内容的变换 > 完整的时间测量 > 解释与图表 > 管理辅助功能。

- 资格测试与审计工具大约占工作量的 10–15%。这是参考比例，**不是**可以忽略真实错误的硬性配额。
- 不建设大型证据框架，不追查全部历史异常，不重写通用 profiler。

## 3. 两个平台的分工

### RTX 5070 Ti

- 公开资料：GB203，6 个 GPC，35 个 TPC，70 个 SM，48 MiB L2，16 GB GDDR7。这些是**预期值，不是实测值**。
- 完整的 GB203 配置为 7 个 GPC、42 个 TPC、84 个 SM。
- 按“每个 GPC 最多 6 个 TPC”推断，活跃配置可能是 5×6 + 1×5 个 TPC。这必须在报告中标为**规格推论**，**不能**作为真值写进 mapper。
- 实卡重点：
  - 普通 CTA 与受支持的 block-cluster 的可执行资源。
  - Green 分区布局与剩余资源。
  - 相同 SM 数量下，不同可控组的类型化容量。

### T10

- 只接受实际的 CUDA 查询结果。预期为 Turing、compute capability 7.5，但 SM、GPC 与裁剪分布未知。**不要**硬编码任何网络规格。
- 没有 block-cluster 路线。运行本课题**不需要**安装 DXR 或 Vulkan。
- Green 需要本机的工具与驱动实际支持。若不支持，使用公开的合法替代方案，或者只做原生容量与普通静态调度的对照。
- T10 同样要运行真实应用并测量完整时间，不能只负责 CPU 或 smoke 测试。
- 不支持的 cluster 格子记为 `NA`。**不得**用软件仿真（例如未优化的 `-O0` 构建）冒充硬件 cluster。

## 4. 连续实验阶段

### E0 — 本地资源与可运行基线

- 在给定的项目、工具与数据根目录内做一次性盘点。不要为了找依赖而反复扫描整块磁盘。
- 填写 LOCAL_PATHS，记录本机版本、设备 UUID 别名、虚拟化与共享状态、温度与时钟的可观测能力。
- 分别构建 `sm_75` 与 `sm_120`（以实测和本地编译器支持为准）。使用已安装的兼容工具。
- **不要**把 RTX 5070 Ti 上的二进制送到 T10 上运行，也**不要**自动统一两台机器的驱动。
- CUDA starter 只用于盘点，或有限的拓扑采样。主 runner 与候选方法仍需实现。
- 优先恢复现成的 3DGS CUDA evaluator 与 Train、Bonsai 场景。Truck 作为留出场景；若它之前被使用过，必须披露。
- 若核心资源不足：生成一次 `LOCAL_RESOURCE_GAPS.md`，继续能做的微实验和 CPU 工作，然后正常结束。不要等待网络授权，不要轮询，也不要反复生成 STOP 文件。

### E1 — 可观测的计算拓扑与可控资源

- 按 `docs/02` 执行。
- RTX 5070 Ti：有限的 cluster 共现测量，以及普通 launch 的覆盖。
- T10：不做 cluster。
- 公共 Green 按本机 API 创建最多 4 种预先登记的 layout，并记录实际 SM 集合、余数、组大小、缺口和 cluster 资格。
- 物理 GPC 图不完整时，保留部分图。**不要**访问私有寄存器、TPC mask 或物理页。
- 若公开接口无法得到任意想要的 SM 子集，就视为控制空间有限，改为在实际能控制的组内测量。**不要**反复重建分区去寻找“赢家”。

### E2 — 容量、并发与损失来源

- 四类有输出的 kernel：计算密集的 uint/FP、对寄存器或合法 shared 资源敏感的、缓存复用的、流式读写的。
- 每类最多三种规模。真实的 kernel 资源来自编译器与 occupancy 查询。
- 对每个实际组，分别测量：
  - 隔离时的服务曲线。
  - 相同任务同时运行时的全部 makespan。
- **隔离标定不能直接代替并发效果。**
- 同一工作量、同一份内存输入、同一总资源份额。所有独立组先全部提交，再统一 join；**不要**逐组串行等待。
- RTX 5070 Ti 可以另测 cluster k=1/2/4/8 中受支持的项，以及一个小型 DSM 共享 kernel。这属于机制实验。
- T10 保持 k=1 的普通路径。
- 得到一张可执行的容量表后，无论物理 GPC 图是否完整，都要完成以下实际测试：同机制的盲分配、按 SM 比例分配、单速率分配、类型化分配，以及置换对照。**不能**只画出容量热图就停止。

### E3 — 唯一候选、强基线与冻结

- 细节见 `docs/03`。
- 候选方法只使用初始化阶段的标定与标定工作集，为每个 kernel 或场景生成计划。正常帧中**没有** CPU 搜索、读回或重新编译。
- 先实现初始化后只读的表。只有在表方案正确且确实有收益时，才做最多 4 个表达等价的编译期常量实例。它们是实现层的消融实验，不是新的算法。
- 允许一个初始化阶段的、有界的 minimax 分配器。不使用机器学习，不做在线强化学习，不使用动态的全局队列。
- 标定时使用少量已登记的并发点来验证模型。**测试时不能选择赢家。**
- 先用一个小型原生任务和一个真实渲染快照，完成“恰好一次”与数值资格测试。之后最多校准 8 个设置或策略。每个策略使用相同的数据和相同的调参机会。

### E4 — 主应用数据（独立配对）

- 两个 workload 入口：
  - W1：真实的 CUDA 3DGS。
  - W2：本地现成的、独立的稀疏 gather 或 CSR 行算子。具体要求见 `docs/04`。
- 若 W2 没有实际来源，只能作为 `SYNTHETIC` 机制实验，**不能**冒充真实应用。
- W1 的两个场景**不是**两个程序。
- 每个平台最多：2 个 workload × 2 个场景或输入族 × 2 条轨迹或请求序列 × 6 个独立进程块 × （8 个策略 + Native 尾锚）= 432 sessions。
- 资格测试、预热与计时都走同一条正常路径。**不能**只在短样本的审计模式下做资格测试。
- 每个 session 先预热 128 帧，且预热时间至少 1 秒；然后测量 512 帧。小型微任务按固定的 epoch 数另外计数。
- 必须存在 Native 作为主对照。所有元数据提取、计划索引、launch 与 join、额外的拷贝，都计入完整时间。
- 模型与计划在测试前冻结。应用场景的计划只来自开发相机，**不能**使用每帧的离线 oracle。
- 若校准与机制实验都没有明显机会，仍然执行固定的 144-session 确认分支，再进入 E6 的完整解释。**不要**为了凑满 432 而强行运行。
- 若连合法的部署都无法建立，就不运行无效的性能格子，但要留下原因，以及已有的容量与原生数据。

### E5 — 留出、生命周期与并发推广（条件式）

- 只有出现可重复的实质增量时才做。做的内容包括：
  - Truck 场景，或 W2 中未使用过的输入。
  - 一个实际可支持的较高分辨率。
  - 启动、计划与编译的回本分析。
  - 最多三对真实独立任务的共置测试。
- 所有参考方法也执行相同的内容。**不能**通过增加卡内总工作量或预取缓存制造优势。
- 共置收益可以在没有单任务加速的情况下研究，但两种指标必须分开报告。**不能**把双任务吞吐写成单帧延迟的降低。
- 没有主效应时，**不要**额外设计极端的 shader 去挽救结果。应交付完整的负结果边界或工程结论。

### E6 — 独立平台收束与合并

- 每台机器正常结束时，交付一份平台报告、数据索引、成本记录、贡献卡和一份简短的导师稿。
- 用户把两个精简包放到同一台 CPU 主机上后，按 `docs/07` 与合并工具做兼容性检查，结果以合并展示的形式呈现，**不是**混池统计。
- **不要**等待另一台机器完成。**不要**根据另一平台的测试赢家，去调整本平台已冻结的策略。
- 代码修订版本不同，则分版本报告。之后可以安排一次明确的复验，但**不能**偷偷合并。

## 5. 不阻塞主线的分支

- 若存在计算或 cluster 方面的异质性，并且部署有增量：继续正式应用与留出测试。内存支线只在有独立证据时才单独判断，本轮不以 NUMA 为主线。
- 若没有完整的物理图，但实际可控的分区有稳定的容量差异：可以完成 capacity-aware 路线，并降低物理因果表述的强度。
- 若只有 cluster 微任务出现差异：完成真实程序的确认。**不能**强迫 renderer 使用 cluster，去制造对旧基线的损失。
- 若原生硬件调度已经足够：保留原生与同机制结果，完成 144-session 确认或最小的已支持范围。最终从六个标签中选择最接近的一个，并写明证据（见第 7 节）。
- T10 没有 Green 时：若标准 cooperative 路径可用，就使用小型、有界的 cooperative 路径。否则只运行原生容量曲线和普通静态映射，并明确说明它们不是物理绑核。缺项就如实记为缺项，**不编造两个 GPC**。

## 6. 只有少数情况需要暂停

只在以下情况暂停并请示用户：
- GPU 设备丢失、系统恢复，或 Xid 等健康事件。
- 需要用户新增付费资源、联网、驱动或权限。
- 必须修改采样算法，或放宽主正确性合同。
- 核心 runner 无法被可信地运行。

以下情况**不暂停**整个项目：普通编译错误、资源查询返回 unsupported、单个候选的数值失败。处理方式是：保留失败记录，隔离该候选，继续其他合法工作。

- 位级差异**不能**通过事后加 epsilon 放行。
- 不为小数位问题开启无限的诊断。直接把该变体记为 `FAILED` 并隔离，不进入计时。

## 7. 实验策略不等于论文保证

- 主结果必须是同一台机器上，相对 Native 和最强简单基线的增量。修复一个人为劣化的分区，**不能**算作部署收益。
- 已有论文已经涉及计算拓扑恢复、静态分配与位置感知调度（见 `docs/01` 中的 S2、S8、S9）。
- 我们的类型化容量与初始化专门化也只是候选。如果一个通用的速度加权贪心算法就能解释结果，那么产出应当是工程结果，而不是新论文。
- 一个或两个具体的正结果，并不等于复现了整个 SKU。
- 只有一张 RTX 5070 Ti，不能声称同一 SKU 的芯片之间存在差异。
- T10 不是同架构的裁剪反事实。
- 规模、质量、程序来源，以及所有 `NA` 项，都必须保留在报告中。

最终状态从以下六个标签中选择，并给出证据：
`PAPER_OPPORTUNITY_WITH_GAPS` / `ENGINEERING_GAIN_ONLY` / `TOPOLOGY_OBSERVED_NO_DEPLOYABLE_GAIN` / `NO_MATERIAL_CAPACITY_ASYMMETRY_IN_SCOPE` / `CONTROL_OR_RESOURCE_LIMITED` / `SAFETY_STOP_WITH_PARTIAL_EVIDENCE`
