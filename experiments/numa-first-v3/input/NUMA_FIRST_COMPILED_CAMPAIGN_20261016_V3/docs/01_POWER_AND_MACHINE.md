# 已批准的T10运行状态控制：执行规则

## 授权边界
用户明确已批准控制T10功耗等运行状态；不用再次为正常的官方功耗/频率设置请求科研批准。在本机现有管理权限和官方支持范围内执行。**不修改驱动/固件/电压，不关闭热保护或故障保护，不强行解锁隐藏功耗上限。** 5070Ti未在本条获得额外硬件控制许可，默认原设定并记录。

## 1. 保存与归还
开始保存GPU UUID、nvidia-smi完整查询、驱动/固件可见版本、supported clocks、当前/默认/min/max power、persistence、现有clock限制、温控service内容/状态/hash。保存可执行恢复清单，正常结束和可捕获异常通过finally/退出处理恢复；SIGKILL/主机断电不能保证恢复，因此恢复清单必须落盘。
所有硬件操作固定指定UUID或PCI ID，不能只用容易变化的ordinal。不得影响另一台或另一GPU。退出时恢复原控制策略；热告警仍有效时不得立即强制写回更高功耗，由恢复后的保护策略按安全条件升档。

## 2. 与现有温控服务协调，不互相抢写
旧证据：`t10-quiet-fan.service` 在温度≥80°C或fan RPM<500连续三样本时降100W，温度≤70°C且RPM≥1000恢复125W。这是历史配置，需要核对当前文件。

优先方案：通过原服务已经存在的配置/维护接口固定实验目标上限，仍保留风扇控制、降额和故障分支。若无接口，只允许一个很小、可恢复的配置补丁：正常目标上限与原热/风扇异常的安全下限分开；禁止取消其降额判断或临时停掉风扇服务。**不要在后台不断用nvidia-smi覆盖保护服务降额。** 修改备份、diff、重载与最终恢复均记录。
无法安全协调时，主实验使用服务能持续维持的保守档，例如实际支持的100W；权限不足只生成一次具体管理员命令清单，不循环sudo提示或绕过权限。

## 3. 两个条件，而非不断搜索频率
P_MAIN：在受支持范围内可持续的固定功耗上限和保守频率；优先当前正常目标（历史125W）但不能只为更高数字强行采用。
P_CHECK：一个较低且支持的功耗档（历史100W可作候选），仅运行指定敏感性子集。

功耗上限并不锁频。`--lock-gpu-clocks`/`--lock-memory-clocks` 只有实际设备支持时使用，选择不高于官方正常支持值、且在主压力下可以维持的频率。内存锁频不支持就记录，不能伪造。未锁频时按active区间实际频率分布报告。

不得把附例频率直接写成T10参数；也不把`-pl`的max当成适合现有散热的安全运行目标。参考官方文档S2。

## 4. 资格用有用工作，不做危险烤机
使用已有内存带宽程序和成熟GEMM各一段，总共约10–15分钟，核查active频率、温度趋势、fan和throttle reason。正常目标应低于实际保护触发点，预留温度余量。必要时一次降低运行档或频率，不为追求0漂移持续调参。
没有主方案收益筛选：选运行状态只看稳定性/安全性，不看M对N胜负。之后冻结，所有方法相同。

## 5. 正式记录与偏离
单独低频采集进程（1–5Hz）记录：requested/enforced power limit、power draw、active SM/mem clocks、temperature、fan/RPM、perf/throttle reason、GPU利用率和monotonic时间。使用本地已有NVML工具；不要每条load起一个nvidia-smi进程。

每个paired block保留首尾Native。状态意外改变：保留整块，标POWER_EPOCH_CHANGED；待稳定后按预注册规则最多补完整块一次，原块也交付。禁止只补候选、删除慢基线、按速度选择功耗状态。主表和all-record敏感性同时保留。
热降额是保护，不将其强制关闭。若设备丢失/Xid/异常风扇，停止GPU并保留记录；普通NA计数器不等于设备故障。

## 6. 命令说明
查询命令可直接使用本机对应版本：`nvidia-smi -i <UUID> -q`、`--query-supported-clocks=memory,graphics --format=csv`。设置命令仅采用查询后有效值：`-pl <W>`、支持时`-lgc <min,max>`、`-lmc <min,max>`。命令本身不是证明请求已生效，必须读回enforced状态。包内不自动执行任何硬件修改。
