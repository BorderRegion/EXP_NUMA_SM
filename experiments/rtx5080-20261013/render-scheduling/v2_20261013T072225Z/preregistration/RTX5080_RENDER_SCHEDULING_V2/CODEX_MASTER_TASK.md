# Codex 主任务书：RTX 5080 渲染访存复用与不规则任务重调度

版本：v2 / 2026-10-13。终点：`RTX5080_RENDER_SCHEDULING_REPORT.md`。
目标：GPU runtime / parallel systems / graphics infrastructure 论文机会验证；不预承诺新颖性、加速或录用。

## 1. 本轮问题与核心变化

用户已把本地主实验卡换成 RTX 5080。研究仍是渲染重排序／重调度，不改成 LLM、编译缓存或测试工具项目。

候选命题：

> 对已经生成、输出彼此独立但读取资源重叠的渲染任务，能否用低成本资源摘要联合规划短任务包的工作集与负载，在有限缓存和多 SM 并发下，获得超出空间排序、纯负载均衡和已有资源分组的端到端收益？若本机存在可利用的位置亲和性，则将其作为额外成本项，而非先验硬件假设。

与 v1 的差别：

- 拓扑审计是**有界机制分支**，不再是所有应用研究的串行前置否决门。
- 主问题包含事前授权的缓存复用／负载路线；未测到 NUMA 时沿这条路线继续，而非临时换题。
- 先在 5080 重建原生 baseline 和负载分解，再决定哪些工作值得改；不复用旧硬件计时。
- 原生任务排序本来可能已有良好局部性，必须给空间排序和资源分组＋均衡强基线。
- 首轮只有一个候选，最多两种执行器布局，不写完整 runtime／编译器／复杂图划分器。

## 2. 本机离线与自主权限

Codex 就在实验主机上。所有编译、运行、读回、统计和归档直接在本机完成。使用已有源码、CUDA、编译工具、模型和场景。先审查构建系统的隐含下载；禁 SSH、远程 Git、代理、在线 API、浏览网页、自动安装／升级和上传缺陷。

缺工具／模型集中登记 `LOCAL_MISSING_RESOURCES.md`。跳过不支持格子，继续安全部分；没有真实应用不能把合成任务称为完整渲染。不要反复申请联网或换路径重试权限提示。离线仅指实验工作流，不指 Codex 客户端连接。

保持旧项目只读。允许新分支／新目录中的代码、有限重构、日志、纯 CPU 分析、合法微基准与既定性能实验。普通模块问题按日志自行修复；每个关键模块最多两轮有明确证据的概念修复。不要将路径错误、拼写修正也机械当作研究 Gate。

不得改画质、采样、像素累积顺序或接受阈值。不得为制造性能空间而禁用原优化、加占位显存、降低 baseline 并发或强制 flush 正式工作负载。

## 3. 假设与证据层次

- RQ1：5080 上观察到的是空间亲和性、普通缓存容量／复用、负载尾部，还是无足够机会？
- RQ2：任务执行组织如何在不改变算术语义的前提下改变访问时间／位置？
- RQ3：低成本摘要能否比仅空间或仅工作量提供有用的任务间复用信息？
- RQ4：联合方法是否优于原生和校准选定的强简单基线？包括特征、排序、队列、拷贝和同步成本。
- RQ5：机制消融、独立轨迹／场景／分辨率是否支持推断，而非测试集选优？
- RQ6：相对原论文、OO-VR、CaT-GS、公开 CUDA 功能及当前后端，究竟新增何种约束、分析或算法能力？

分开报告 `PHYSICAL_OR_EMPIRICAL_AFFINITY`、`CACHE_REUSE`、`LOAD_BALANCE`、`END_TO_END_EFFECT` 与 `NOVEL_METHOD`。一个大加速数字不能自动建立后面所有主张。

## 4. E0：硬件迁移、资源盘点与计划冻结（CPU 为主）

只读查询实际 name、device ordinal/UUID、VRAM、cc、SM count、L2、shared memory、driver、OS、runtime/toolkit、主机编译器和 profiler。

5080 官方参考规格见硬件文档；不得把参考值写成实测结果。OS 以当前主机为准，不假定仍是 Windows；不进行 OS/WSL 迁移。

确认本地编译器接受 `sm_120` 或已存在的可兼容 PTX 路线；所有选定 kernel/第三方扩展都需兼容。不照抄 B200 的 `sm_100a`；不使用只有 `sm_89` cubin 的旧产物。旧 PTX 能 JIT 运行只证明兼容性，不证明最佳原生性能。JIT/缓存准备进入 setup 和生命周期账本，不混进稳态 kernel 时间。

最多检查两个已在本地的 CUDA 渲染实现，首选可修改完整 tile rasterization 的 3DGS。默认以最成熟、能原生正确运行且可修改的一个作为主程序；Graphdeco 原版只是可审查来源，不默认是最快 baseline。gsplat／Flash-GS 等仅在本地可用且质量合同兼容时列真实对照，不为本轮联网移植。

冻结两开发场景和最多一留出场景，按预先声明的资产规模／室内外／几何差异选择，不能看方法收益后挑。每开发场景校准轨迹和测试慢／快轨迹分离；分辨率默认 1920×1080。留出资产在方法冻结前不作性能调参。

输出新 `5080-baseline-ready` 对应实际 commit/tag；只在编译、正确执行与初始计时真正通过后建立，禁止将源码下载状态叫可运行 baseline。

## 5. E1：原生剖析与有界硬件审计

首先运行完整原生流水线：preprocess → 原排序/binning → render → 实际所需结果交付。保存 GPU 完整区间、各阶段和 CPU submit-to-completion。不要预生成所有中间数据后把孤立 render 测试当端到端。

场景校准中记录任务数、tile 列表长度分布、独立资源数的代理、工作倾斜及目标阶段占比。如果主瓶颈是上游、CPU 或算术，仍可做少量候选机会测量，但不得先贴 memory-bound 标签。

硬件诊断只访问本进程申请并初始化的数据，最多45分钟 worker。相对本机查询的 L2 测 0.25/0.75/1.5/4 倍工作集、低并发 dependent-index-chain 与代表性并发 gather，区分普通load/L1-bypass及缓存准备条件。观察实际 SM；不预测物理页、不读其他进程、不修改驱动。细节见硬件文档。

路线选择：

- **A：真实可利用亲和性**。独立数据支持位置×数据交互，且合法匹配控制带来可复现效果；候选带拓扑项。
- **B：未证实或不可控制的亲和性**。主候选不带拓扑项，继续实测缓存工作集、资源复用与负载冲突。
- **C：应用／工具缺失或全部诊断不足**。完成可支持微测、CPU分析和资源清单，不编造应用结论。

A/B 是本轮预先批准的分支。B 不需要再次请求批准，但结果标题必须写 cache/load scheduling，不能称“5080 NUMA 已建立”。没有信号不继续无限猜 topology。

## 6. E2：安全执行器与最小机制对照

先把 logical tile ID 与 grid/block ID 解耦，在不改 evaluator 算术的情况下实现 identity 与 permutation。确认完整 tile 恰好执行一次、输出仍写原像素、每像素 Gaussian 顺序不变。

默认第一种执行器：原 launch 规模的 indirect-tile dispatch。它只表达映射，不保证 block 实际时间顺序。

确有局部串行复用需求且第一种表达不了时，允许第二种：**短寿命、有限任务包的动态领取器**，每 CTA 一次领取一个小包，顺序执行包内完整 tile。所有包在 launch 前建好；无全局自旋等待、无跨kernel通信、无必须等指定SM才能结束的任务。

最多这两种形式。将共同 executor 参数在校准期冻结，B1–B5/M/C 使用同一 evaluator、同样 worker/bundle 资源上限；不可只给 M 更合适 occupancy。B0 保留原生最优实现，不能用一个慢的新框架替换生产基线。

先进行96个小型整数 gather 配置：4个L2相对规模×3个复用等级×2个负载倾斜×4种固定调度。说明合成数据用途，不模拟出理想亲和后称真实硬件发现。独立CPU校验任务覆盖与输出。

合法性失败自动诊断和最多两轮有据修复；仍不成立则隔离该 executor。两者都失败，结束应用分支并完成报告，不转向无限FP调查。

## 7. E3：唯一候选与强基线校准

候选为**容量约束的资源复用＋负载协同任务打包**。代码层定义与基线在 `METHOD_AND_BASELINES.md`。若 A 成立，加一个已经测量且验证的访问亲和项；否则该项严格为零，不创建虚构物理域。

不实现大模型、RL、完整图划分或动态数据复制。当前帧 `ranges/point_list` 上提取至多8或16个资源样本／tile，工作量使用可廉价获得的列表长度等代理。前瞻最多使用当前已完成producer的数据，不用本帧事后贡献计数或未来相机作为免费特征。

强基线调优权平等：每个有参数的策略最多12组预注册配置、每组两次独立校准重复。候选也最多12组。若计算一个高质量离线排序作参考，其运行成本要么计入，要么明确是非部署诊断；不得写成已经实用的性能。

先做少量预注册在线pilot：包含完整上游和调度开销。若不存在相对校准最强简单策略的信号，也完成较小的独立确认，不以pilot阴性直接取消所有验证，更不扩算法救结果。

看测试结果前冻结：方法、摘要、桶、任务包上限、topology使用标志、executor、所有基线参数、校准最强基线 B*、场景/轨迹/时间区间、随机顺序与统计方法。

## 8. E4：主应用矩阵或阴性确认矩阵

**完整路线**：2开发场景×2测试轨迹×最多10策略×5新进程块，最多200个session。缓存路线实际9策略时180个session，不凭空补第10个。

每session：完整路径预热至少256帧且至少2秒；固定512帧测量；应用输入由预定simulation time决定，不能由方法运行速度决定。若renderer太快不能在256帧达到2秒，增加真实热身帧且记账。

**无pilot增量路线**：2场景×2轨迹×3策略（B0/B*/M）×3进程块=36session，输入同合同。完成后输出无空间或不确定，不自动打开大矩阵。

完整GPU帧时间必须从新增特征/队列与上游开始，到必要消费/结果可用结束；preprocess、原排序、渲染、额外copy都计入。独立CPU端到端一并保留。所有步骤原生也需要的共同成本不删；只在单独标记的micro replay中缓存中间结果。

block是统计重复单位，策略顺序平衡随机化；同进程共享场景实际资源、各策略独立重置本身状态。没有固定先跑baseline的借口。不能因为M比其他策略先暖cache而获益。

若使用CPU规划/读回，必须计入线上关键路径。GPU-only和CPU辅助不能偷换口径；CPU原型只能提供机会估计时要降级结论。

## 9. E5：留出、机制与生命周期

冻结主方法完成后，支持时自动执行：

- 最多1个独立留出场景×2轨迹×3策略（B0/B*/M）×5块=30session。
- 两开发场景的同一预定fast轨迹，2560×1440，3策略×3块=18session。

是否有资源／规模安全在E0决定；不按测试正负选择是否运行留出。在阴性确认路线、预算不足或正确性阻塞时自动跳过并说明。4K不进首轮；不因为5080更强就无限扩范围。

最多6次单独profile，使用正确的cache/replay配方，不能默认flush后用所得counter解释自然热缓存结果；不能把重型profile帧混入正式p99。

报告设置／建图／分配亲和标定一次成本与每帧维护，N=1/100/1000生命周期仅对真实覆盖范围计算，外推估计单列。回本帧数只在净节省为正时定义。

缺counter不阻塞端到端结果，但必须降低“缓存/NUMA导致”的机制结论。任务摘要独立抽样与实际资源集合对照；只可称footprint/traffic proxy，不能冒充DRAM字节。

## 10. E6：一次性论文判断，不再新建小Gate

最终状态为以下之一：

- `AFFINITY_AND_CACHE_OPPORTUNITY`：A路线、有效控制与消融、强基线增量、完整成本均有证据。
- `CACHE_LOAD_OPPORTUNITY_ONLY`：无NUMA主张，但缓存/负载路线有新约束或方法增量的初步证据。
- `ENGINEERING_GAIN_ONLY`：有加速，现有排序/均衡/分组机制已能解释，或缺新方法。
- `NO_INCREMENTAL_OPPORTUNITY_ON_5080`：在已测合法范围内没有强基线外的可用空间。
- `BLOCKED_LOCAL_RESOURCE`：缺真实应用／支持工具，不能当性能否定。
- `INCONCLUSIVE_WITHIN_BUDGET`：资格、噪声或预算不足；写清何处未知，不自动再跑一轮。

约5%独立端到端净收益是进入论文级扩展的参考，不是录用标准。小而稳定的效果如实报告；没有新方法不因大数字判GO。反过来不能把低于门槛写成效应为零。

不得沿用旧反复转向：没有收益就收束当前候选；不在本轮再新增第三种executor、第二种布局、子tile切分、learned预测器、缓存容量软件隔离器或完整编译器。

主报告必须回答：5080上实际支持什么；A/B为何选择；最强基线是谁；真实资源复用与尾部证据；每帧额外成本；正确性范围；所有负例；独立验证；相关工作区别；仍缺外部验证什么。

## 11. 预算、停止与完成度

总上限12 GPU-worker小时（setup/编译占用该worker/等待/profile均计）。E0=0.5h、E1=1h、E2=1.5h、E3=2h、E4=4h、E5=1.5h、预留=1.5h。拓扑部分单独≤45min。CPU-only开发/分析另计；不承诺整项研发12小时完成，也不要求跑满。

应用显存保持至少max(2GiB,设备总VRAM15%)余量；按现有可用值动态核查，不把16GB全部用尽。诊断最多512MiB且≤当前free10%；输出软上限12GiB/硬上限24GiB。不要删除用户模型或旧raw。

单次普通微诊断kernel目标≤20ms，从小规模逐级扩大；有限Q只处理当前帧，不跨帧永久常驻。进程timeout不能代替GPU安全。

不改功率/时钟/驱动；记录温度、时钟、后台使用及API实际配置。受控低功率实验不在本轮。GPU设备丢失、OS恢复或健康异常立即停GPU，CPU报告继续，不循环重现。

中间每个自动状态写日志，不反复向用户汇报“请再批准下一小步”。只有要改合同/系统/付费或设备不健康时请求一次决定。正常情况直接交主报告、贡献卡、可复算数据、预算、缺失清单和导师短稿。
