# OP-FUSED T10 独立审阅与执行决定

审阅日期：2026-10-15。材料：用户上传的 `OP_FUSED_T10_REVIEW_AND_BASELINES_20261015.zip`。

## 1. 决定

**部分验收：原生基线和受限成本记录可保留；新方法未实现，不能验收为完整方法实验，也不能作为算法或推理负载的 NO-GO。**

保留 `IMPLEMENTATION_OR_RESOURCE_LIMITED`。建议把机器字段拆为 `native_baseline_campaign_complete=true`、`candidate_implemented=false`、`method_campaign_complete=false`，不覆盖原始报告。下一步不换题，不扩大独立 baseline 数据；先交付可修改的 SM75 Tensor Core 数学主体，再接续原来的算子内调度任务。

本文是附件审阅与 CPU 复算，不是 GPU 复现，也没有另做当前文献检索。下面把原材料支持的事实、代码推论和后续设计建议分开。

## 2. 独立复核范围

- 清单覆盖 2,090 个文件，大小和 SHA-256 全部一致。清单自身、`GPT_READ_FIRST.txt`、`PACKAGE_SCOPE.txt` 另有三项未列入该清单。
- 读取 62 个运行注册项，没有发现记录中的 GPU 子进程执行窗口重叠。
- 重建原生 936 个 case-block／4,248 phase，独立强库 312 个 case-block／1,248 phase，逐请求层 35 个 case-block／140 phase。合计 1,283 个有效 case-block、5,636 个正式 phase。
- 从逐 case 保存的 phase 数值重算 354 项配对效应及同配方 20,000 次 bootstrap 区间，与派生报告一致（最大浮点绝对差约 7.1e-15）。这验证统计计算，不消除实验设计和环境限制。
- 从 284 个逐请求 phase 的原始数组分别重算 36,352 个 CPU-ready 样本和同数的 event 样本，两类均值与记录一致。
- 从原始 Graph 树重建 624 个 kernel 节点记录，与包内 census 一致。
- 48,308 条正式输出检查摘要均记载通过，最大归一化 Frobenius 约 0.000289244。没有输入／输出 tensor，未独立重算矩阵乘法或实际误差。
- 四份已保存 SM75 Triton probe PTX 都没有 `mma.sync`／`wmma.mma`／`wgmma.mma`，而存在普通 `fma.rn.f32`。这是这些具体产物的证据，不能扩大为所有 Triton／Turing 路线都不可能使用 Tensor Core。
- 五个请求时源码 hash 与获锁时快照不同，包内已经披露。独立检查了真正用于各 native 阶段的 capture/phase/grouped/layer/attention 函数 AST，各自稳定。保留请求时与启动时的不同角色；这不是新的 GPU 失败，也不是完整形式等价证明。

完整脚本和结果见 `independent_audit.py`、`independent_audit.json`。

## 3. 实现层级：正确地没有用慢原型冒充，但核心仍未做

原报告和代码均表明，CORE/BAL/CACHE/FULL/ABL 未实现；没有新的 producer sideband，也没有 F0S0/F1S0/F0S1/F1S1 四格。

可用的是：

1. 逐 problem cuBLAS／cuBLASLt 调用，经 Graph 预录重放；
2. 后发现的原生 `cublasGemmGroupedBatchedEx`，按相同 M/N/K 做标准 grouping；
3. PyTorch 已编译的 SM75 attention，以及 decode-only 的 GQA 查询布局适配；
4. 固定外部 route/count 下的 pack、gate/up、SwiGLU、down、combine 组合层。

不可用的是一个本地完整、可修改、已合格的 Tensor Core grouped visitor。库内能调用到 Tensor Core，不表示本地具备该库内核的可改源码。限定搜索缺少源码是资源阻塞，不是新方法不成立。

用户要求“不增加小调度 kernel”仍然适用于待实现候选；不能因为尚未实现就记为该贡献已达成。逐 expert LIB 是已有参考，可以保留，但不能改名为 FULL。

## 4. 最有价值的新增基线发现：kernel 节点数不是速度的充分条件

本轮同 Graph、同缓冲的留出库比较为：

| 范围 | native grouped / per-expert | 探索性95%区间 |
|---|---:|---:|
| 24个留出算子，device interval | 1.318508 | [1.302484, 1.336112] |
| 6个留出post-route层，CPU-ready | 1.040130 | [1.022196, 1.059263] |

这只是两种已装库调用方式的对照，不是 FULL 的效果，更不是动态 MoE 服务结论。

逐 case 图结构揭示了相反例子（时间比 <1 更快）：

| case | per-expert节点 | grouped节点 | grouped/per-expert ready |
|---|---:|---:|---:|
| grouped-025 | 8 | 1 | 2.3527 |
| grouped-093 | 32 | 1 | 0.7725 |
| moe_layer-009 | 30–34 | 10–14 | 1.2588 |
| moe_layer-017 | 46–50 | 10–12 | 0.8586 |

这些例子不是新挑选的评估集合，仅用于解释既有全表；全部 54 个 case 的节点和效果在 `graph_and_cost_by_case.json`。

`grouped-025` 的两种图还记录相同 kernel 符号及 block 配置：8个 `[16,2,1]` grid 对一个 `[16,2,8]` grid。`grouped-093` 类似，是32个 `[43,1,1]` 对一个 `[43,1,32]`。不能仅因符号相同就证明内部数据路径、参数或机器资源完全相同；也不能仅因节点减少就断言复用或吞吐更好。

**允许的结论：**不增加人为的细碎调度步骤很重要，但最终仍要比较计算效率、访存与任务组织的净效应。不能把“更少 kernel”当作性能单调保证。旧库可能含自己的 split-K 和必要归并，这不等于本研究可以删除那些步骤。

## 5. 温控是实际运行条件，不是一句笼统的“噪声”

包内保存的既有 `t10-quiet-fan.service` 记录：达到80°C或低风扇转速保护条件时降到100W；冷却至70°C且风扇正常后恢复125W。此次未修改该服务。

重建结果：原生 phase 中477个125W、3,769个100W、2个过渡；强库 E1 有125W/100W/过渡，但强库留出 E3 的576个phase及层 E4的144个phase全部标记100W。

因此：

- 开发集选择是该温控策略下的经验选择，不能当作固定125W的最优选择。
- 同时，不能把强库留出的1.3185全部推给功耗切换；其记录全为100W。
- 100W标签一致仍不等于温度／频率完全固定。每个数字保留适用条件和首尾敏感性。
- 125W与100W子表样本组成和发生时间不完全相同，不能据此单独声称功耗造成策略反转。

下一轮不关闭保护、不自行改功耗／风扇。先沿用真实服务和相同热身/随机顺序。若要形成受控的另一功耗状态，由用户一次授权安排散热或明确配置；不要把它变成一串核查任务。候选自己触发保护也属于部署代价，不能只排掉慢状态。

## 6. 原调度规则的结构性问题属实，需要我方修正设计预期

包中的 work_budget 由开发集 K/BK 的75分位乘2得到，当前 BK=32，work_budget=128。K=4096时 k_e=128，因此：

`floor(work_budget / k_e) = 1`。

全部32个 K=4096 grouped 计划都只能 q=1。独立复算显示，在BM32/W56的示例下，96个计划里59个最大包长≤1；BM64/W112时为75个。它们是计划结构推论，不是 GPU 性能。

q=1并不保证输出tile顺序与原生相同；但不能用这些点检验多tile包的复用。不能为了让曲线更漂亮而加token、改专家路由或用测试结果上调预算。

正确处理：保留q=1负控制，先在实际数学主体上建立q>1真正可达的开发输入与packet分布；确认参数的物理含义。若以后修正规则，建立显式版本/新确认清单，不重标旧测试为未见。

## 7. 其他限制：记录即可，不另开大审计

- FULL和新融合均未实现；attention布局适配不是新内部调度。
- post-route层不包括router/count/scan；静态描述符在热计时外构造。它不是完整动态MoE/LLM。
- 动态attention同时变化prefix/layout、Q/长度、三组KV，不能由差值算纯metadata或缓存贡献。正式检查只覆盖预定的几个序列项，不是每个重复步骤完整重验。
- `attention_decode-047` 的reserved峰值超过原余量规则，活跃量与遥测口径不同；原标记 `MEMORY_MARGIN_NOT_QUALIFIED` 合理。不要由此宣称设备OOM，也不要为了强制通过改小逻辑输入。新实现阶段让不同参考/Graph按生命周期释放，避免验证器持有所有对象造成非生产峰值，所有实现使用同一内存合同。
- 保留13条正式case失败；Graph零边查询与runner引用保留是工程记录，不是13个编译器错误。
- 已知旧hash/获锁快照差异可在今后执行入口一次修正，不重跑整份库矩阵。

## 8. 接下来应做什么

### 必须优先：补齐可修改的 Tensor Core 数学主体

一次性提供完整、兼容本机SM75/CUDA/宿主环境的源码与实际依赖，优先沿已选grouped来源；不是再安装一个只有二进制算子的Python包。Codex本机仍离线，缺文件集中列一份资源清单，不循环请求联网。

拿到主体后，顺序是：原生visitor→普通均衡/固定复用→唯一候选→合法fusion→固定的小型完整层确认→有依据再跑原正式矩阵。不是再次只采几千个LIB phase。

### 实现不应被元数据准备反客为主

新映射嵌在visitor；局部sideband由已经合法就绪的producer产生。不新增外置planner、每expert CPU发射或调度D2H；必要全局归并保留，同融合等级的基线也保留。当前闭源grouped库不是可修改主体的替代品。

### 控制开支与连续性

剩余原T10预算约12.72 worker小时；不重置16小时总账。没有可改主体时停止新的baseline-only计时，完成CPU接口和一次资源清单后正常结束。资源齐备后正常工程问题自行处理，接续同一研究，不逐小步等待审批。

## 9. 论文结论

当前没有新方法收益，也没有新方法的负结果。它提供了更强的库基线、实例化范围和温控条件，是后续比较的基础。

Grouped库有强烈shape依赖的正负例，但不自动授权另开“Auto library selector”论文；已有聚合结果和少数正例也不能保证FULL会赢。

**最准确的状态：数学主体适配受阻，方法验证尚未开始。下一份成果应优先是可修改的高效算子内实现及同融合对照，不是更多原生库统计或新的研究名称。**
